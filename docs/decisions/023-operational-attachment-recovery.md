# ADR 023: Operational snapshots and attachment recovery

Status: implemented 2026-09-22. Supplements ADR 013; its local-only recovery limitation is superseded. Local Docker acceptance passed (docs/evidence/docker-backup-2026-09-22.json); staging and natural scheduling remain pending.

`backup:create` exports one PostgreSQL repeatable-read snapshot to `pg_dump` and reads the attachment inventory from the same transaction. Every attachment row, including unbound and soft-deleted rows, contributes its original disk/path, size and SHA-256 digest to a versioned `attachments.json`. File bytes are read through Drive and archived as `<id>.bin`; disks can coexist without path collisions. Missing files fail the backup. Application attachment paths are immutable and storage migration retains the old objects; external mutation/deletion during a backup is not supported.

The offsite publisher uploads and downloads each artifact to verify its hash, then publishes and checks `COMPLETE` last. It does not overwrite a completed prefix. The local marker and success timestamp follow remote completion. Incomplete snapshots never participate in retention or latest-snapshot selection. Source disk credentials remain separate from backup credentials, and backup deletion permission is not required.

The daily shell delegates to the same command tested against S3. The scheduler mounts `backups:/backups:ro` and retains writable local uploads. The monthly `backup:restore-test` validates checksums and safe archive entries, restores a dedicated temporary PostgreSQL database, matches every manifest entry to its restored row and verifies all bytes. It writes and reads isolated keys on each original disk and deletes those keys, without changing original file keys. A bound record is still required unless `--allow-empty` is explicit.

`backup:verify-snapshot` checks integrity before destructive database recovery. `backup:restore-files --apply` checks the entire archive against the restored database before writing original disk keys, and reads back every restored file. `make restore` stops application services, invokes these commands through the restore script, reconciles runtime state, and reopens traffic only on success. Partial file restoration is retryable while traffic stays stopped. Legacy local snapshots remain supported; the drill rejects non-local rows in a legacy snapshot.

No schema migration, new dependency, normal-runtime educational resource, or release acceptance is introduced. Direct real-provider command acceptance is complemented by the dated Docker exercise proving volume permissions and manually invoked recovery. Neither proves natural scheduling, staging or production supervision.

The offsite monitor scopes both provider listing and assessment to BACKUP_S3_PREFIX (default adula). A recent snapshot requires nonempty database.dump, uploads.tar.gz and SHA256SUMS plus COMPLETE in the same immediate timestamp directory. A zero-byte marker is valid. Legacy uploads without a completion marker are not accepted by monitoring. A prefix change invalidates the setup inspection fingerprint. Object listing remains a presence/freshness check; checksum verification belongs to publication and restoration.
